## 0. Key finding before anything else: there is no single "5-plot-type module"

The brief assumes one module produces 5 plot types. It doesn't. There are **three independent, non-communicating rendering systems**, plus a fourth desktop-config cluster that feeds only one of them:

| System | Plot types it actually offers | Library | Where it renders |
|---|---|---|---|
| **A — `datavisualizer.py`** (desktop) | Bar, Box, Violin, Raincloud, *(Forest — defined but dead, see §0.1)* | matplotlib/seaborn | Desktop GUI, static PNG/SVG/PDF export |
| **B — `plot_designer.js`** (HTML) | Bar, Box, Violin, Raincloud, Forest, Estimation (6) | Plotly.js (client-side) | Interactive "Plot Designer" section embedded in every exported HTML report |
| **C — `report_charts.py` → `_build_group_comparison_chart`** (HTML) | Only ever Box (`go.Box`), regardless of what the underlying test/plot_type was | Plotly (server-rendered) | Static "Charts" section of the same HTML report, **directly above** the System B designer |

Only **System A** has exactly 5 named functions matching "bar, box, raincloud, +2 more" (`plot_bar`, `plot_box`, `plot_violin`, `plot_raincloud`, `plot_forest`). System B has 6 (adds "Estimation"). System C isn't a 5-type system at all — it's one hardcoded Box-plot builder that fires for any group-comparison result.

**Consequence for scope:** Philipp's six "must be identical everywhere" rules (font, frame, palette, error bars, marker edge, point-fill-black) can't be satisfied by editing one file. Systems A and C are both Python and could share one constants module trivially. System B is client-side JavaScript baked into an HTML template at export time — it cannot import a Python module at runtime; keeping it in sync requires serializing shared values into the page (see Phase 3). This materially changes the size of the Phase 4 effort depending on which system(s) are in scope — flagged as an open question at the end of this report.

### 0.1 Additional finding: two of System A's five functions are effectively dead or bypassed

- `plot_forest` (`src/visualization/datavisualizer.py:2956`) and `plot_roc_curve` (`:2921`) are **never called from anywhere else in the repository** (repo-wide grep found only their own `def` lines). They are defined but unintegrated.
- The real production dispatch for exported figures is `src/analysis/analysis_core.py:1342-1394`, which calls `DataVisualizer.plot_bar` / `plot_box` / `plot_violin` / `plot_raincloud` **directly**, keyed on a `plot_type` string. A `"Strip"` plot type also exists in that dispatch (`analysis_core.py:1373-1385`) but silently falls back to `plot_box` — it is not a real 5th type, just an alias.
- Separately, `DataVisualizer.plot_from_config` (`datavisualizer.py:2583-2841`) is a **second, parallel dispatcher** to the same four functions, but it is only reachable from the *live preview widget* in the desktop Plot Aesthetics dialog (`src/visualization/plot_preview.py:220`), never from the export path. Critically, `plot_from_config` is the **only** call path that invokes `StylingManager.apply_unified_styling` (`datavisualizer.py:2809`) and `FontManager.apply_font_safely` (`datavisualizer.py:2795`) — i.e. the "unified styling" machinery that reads `font_family` and other config only ever touches the **preview**, never the **final saved figure**. This is a second, independent inconsistency mechanism (preview vs. export) layered on top of the cross-plot-type one the brief asked about.

So System A's real, live plot-type set is **Bar, Box, Violin, Raincloud (4)** for exports, styled without the unified-styling layer; `plot_forest`/`plot_roc_curve` are orphaned code.

## 3. Classification: global token vs. plot-specific

| Attribute | Classification | Justification |
|---|---|---|
| Font family | **Global token** | No plot-type-specific reason for Bar to use a different typeface than Box. Purely a shared-value bug. |
| Font size hierarchy (title/axis/tick/legend) | **Global token** | Same reasoning — a title should be the same size regardless of geometry. |
| Frame/spines presence + linewidth | **Global token** | An axes border is a page-chrome decision, not a geometry decision. Raincloud's separate `frame_thickness` param has no geometric justification — it's an accidental fork. |
| Frame/spines **color** | **Global token** (distinct from presence/linewidth) | The border color is page chrome, same argument as linewidth — but it's a *separate* attribute and currently forks three ways (§2.4): A leaves it to the ambient matplotlib/seaborn default, B hardcodes `rgba(22,49,58,0.75)`, C draws no border. Making the frame consistent requires pinning color, not just width and which sides. Note this makes explicit that unifying System C means it *gains* a drawn border (with the shared color) that it doesn't have today — an intended visible change, flagged for the review checkpoint alongside the black-fill change. |
| Color palette / group→color mapping | **Global token** | The whole point of a palette is that "Group A" means the same color everywhere the user looks. This is the highest-impact global token in the audit — it's currently forked at least 3 ways (A's bright palette, B/C's teal palette, plus ~5 more duplicate literals of the same teal set). |
| Error bar style (color, capsize, linewidth, cap style) | **Global token**, with a plot-specific *presence* flag | The visual rendering (color, linewidth, cap style) should be one shared spec. Whether a given plot type *shows* error bars at all (e.g. raincloud arguably shouldn't, since the raw distribution is already visible) is a legitimate per-type decision — but that's a boolean, not a style fork. Currently both the boolean AND the rendering diverge uncontrolled. |
| Data point marker: edge on/off, color, width, size | **Global token** | Same argument as font — a data point is a data point regardless of which background geometry (bar/box/violin/cloud) it's plotted over. |
| **Data point fill color (black rule)** | **Global token** | This is explicitly the rule Philipp stated. It currently holds in 3 of ~13 combinations (§2.4). Given both HTML-facing systems (B, C) always use the group palette instead, the audit surfaces a decision point for Phase 3/4: either (a) make black the enforced global token everywhere including HTML reports, a visible UI behavior change to the plot designer's current default, or (b) revise the intended rule. Not this report's call — flagged for the review checkpoint. |
| Gridlines (on/off default, color, style) | **Global token for style; plot-specific for the on/off default** | Grid line color/width/alpha should be one spec. Whether grid is on by default could reasonably differ (e.g. off for a clean box plot, on for a dense forest plot) — but currently no plot type turns it on by default in any system, so this is theoretical, not an active fork worth preserving. |
| Tick style (direction, length, width) | **Global token** | No geometric reason ticks should be shorter on one plot type than another. |
| Legend style (frame, font) | **Global token**; position/show-condition is closer to **plot-specific but should still be intentional, not accidental** | Frame and font: no justification for variance. Position/show-condition (e.g. box/violin in System A require `show_points` to show a legend at all) looks like an accidental omission, not a deliberate design choice — worth revisiting in Phase 3/4, but the *decision* of "should this plot type show a legend" is legitimately a per-type call even if the current per-type answers look unintentional. |
| Figure export settings (DPI, format, background) | **Global token** | An export preset (DPI, transparency, format list) is a user/output-target decision, unrelated to plot geometry. |
| Axis label / title capitalization & wording conventions | **Global token** for the *mechanism* (should text be transformed, and how); **plot-specific content is fine** (e.g. Raincloud legitimately needing to swap x/y label assignment for horizontal orientation is geometry, not a style bug) | The specific issue found — Bar uniquely appending a measure/error suffix to the y-axis title — is a content decision that arguably belongs everywhere error bars are shown, not just Bar; worth a product decision, not purely a bug. |
| **Plot-specific, correctly so (not global tokens):** bar width, violin bandwidth/KDE smoothing, jitter/beeswarm amount, raincloud's half-violin offset and box-overlay width, forest's row spacing, capsize *presence* per type (see error bar row above), point size-scale factor differences that stem from genuinely different overplotting density per geometry (though the specific factors found — `/8` for raincloud scatter vs. raw `point_size` for others — look more like accidental inconsistency than a deliberate density-aware choice; worth a second look in Phase 3/4, not asserted as correct here) | **Plot-specific** | These vary because the underlying geometry legitimately differs — a violin needs a bandwidth parameter a bar chart has no use for. This report does not flag these as bugs. |

## 4. Phase 2 — Reference check (brief)

- **GraphPad Prism**: styling is attached to a *graph format*, not to an individual graph. A user edits fonts/frames/colors/error-bar style once in the "Format Graph" dialog (or a saved format template) and that format cascades to every graph built from the same "family" (e.g. every graph derived from one data table), while data-driven aspects (axis ranges, which columns are grouped) stay per-graph. The key idea: **one style object, referenced by many renderers, with an explicit override path when a specific graph legitimately needs to differ** — the override is a deliberate, visible action, not a silent hardcoded literal buried in a plotting function.
- **matplotlib `rcParams` / stylesheets**: a single dict (or a loaded `.mplstyle` file) holds every visual default (font, spine linewidth, tick direction, grid alpha, figure DPI/facecolor); every `plt.plot`/`ax.bar`/`ax.boxplot` call inherits from it unless a call explicitly overrides a specific kwarg. The pattern that makes this durable: **the shared defaults are looked up once by matplotlib itself, not re-declared per call site** — so consistency is the path of least resistance, and a per-plot override is opt-in and local (visible right next to the call it affects), not an independent copy of the whole style.
- Sanity check for Phase 3: BioMedStatX's current architecture is the inverse of both patterns — every plot function (and, worse, every one of 3 separate rendering systems) re-declares its own copy of the "shared" values, so consistency currently requires **remembering to copy correctly**, the opposite of Prism's and matplotlib's "consistency by default, override by exception" model.

## 5. Phase 3 — Proposed architecture (proposal only — no code changes)

### 5.1 Where the shared style lives

Because the three systems span two languages (Python for A and C, JavaScript for B) that don't share a runtime, one literal shared Python object cannot directly serve System B. Proposed structure:

1. **`src/visualization/style_tokens.py`** (new file) — a single Python source of truth: a small `PlotStyle` dataclass (or plain module-level constants, matching the existing lightweight style of the codebase) holding every attribute classified "global token" in §3: font family, font size hierarchy, frame linewidth/color, the canonical palette, error bar spec, point marker spec (including the fill-color rule once Philipp confirms it), grid spec, tick spec, legend spec (frame/font — not position), export defaults (DPI, format list, background).
2. **Python consumers (Systems A and C)** — `datavisualizer.py`'s `plot_bar`/`plot_box`/`plot_violin`/`plot_raincloud` and `report_charts.py`'s `_build_group_comparison_chart` import `style_tokens` directly and replace their hardcoded literals (e.g. `datavisualizer.py:1751`'s `'color': 'black'`, `report_charts.py:728`'s inline `palette = [...]`) with references to the shared object. This is a same-language, same-process import — no serialization needed, minimal diff per call site (swap a literal for `STYLE.point_fill_color`, etc.).
3. **JS consumer (System B)** — `plot_designer.js` cannot import a `.py` file. Proposed: `html_exporter.py` (which already serializes `plot_data_json`/`stats_summary_json` into the report template, `html_exporter.py:167`) additionally serializes `style_tokens.py`'s values into a `plot_style_json` blob injected the same way. `plot_designer.js`'s `state` object initializes its style defaults (`defaultPalette`, font size defaults, `axisThickness` default, etc., currently hardcoded at `js:135-152` and in the HTML `value=`/`selected` attributes) from that injected JSON instead of from its own literals. The **interactive, user-adjustable nature of the designer is preserved** — the shared tokens become the *default* state, not a hard lock; a user can still drag a slider to change axis thickness for their one export, exactly as today.

### 5.2 How a future single-place change works

Example: "make all frames 1.5pt instead of 1pt." Today this requires editing at least 6 independent locations (A's `axis_thickness=0.5` defaults × 3 functions + Raincloud's separate `frame_thickness=0.7`, B's UI default for `pd-axis-thickness`, and confirming C has no equivalent to add). Under the proposal: change one field, `style_tokens.PlotStyle.frame_linewidth`, in one file. Systems A and C pick it up on their next run automatically (same-process import). System B picks it up for every **newly exported** report, because `html_exporter.py` re-serializes the current `style_tokens` value into `plot_style_json` at export time — already-exported HTML files are static snapshots and correctly keep whatever style was current when they were generated (flagged so this isn't mistaken for a bug: old reports won't retroactively update, and that's expected for a static HTML artifact).

### 5.3 Keeping plot-specific attributes flexible

Plot-specific values (bar width, violin bandwidth, jitter amount, raincloud's half-violin offset, KDE smoothing) stay exactly where they are now: local variables / function parameters inside each plot function or `buildTraces()` branch. They are explicitly **not** added to `style_tokens.py` / `plot_style_json`. The dataclass boundary is the enforcement mechanism — if it's not a field on `PlotStyle`, it can't accidentally leak into "shared," and a reviewer can audit drift risk by checking whether a new hardcoded literal duplicates something already in `style_tokens.py`.

### 5.4 Regression-safety plan

1. **Baseline capture (before any Phase 4 edit):** for System A, render all 4 live plot types (`plot_bar`/`plot_box`/`plot_violin`/`plot_raincloud`) against one fixed synthetic dataset (same approach the repo already uses for its statistics golden references under `tests/golden/` — this audit found no equivalent golden-image mechanism for plots, worth adding) and save the PNGs. For System B, use the same fixed dataset through the HTML export path, screenshot each of the 6 `pd-plot-type` options in the designer (browser automation), save as baseline images. For System C, capture the rendered Plotly figure's JSON spec (not just a screenshot) for the group-comparison chart, since it's deterministic and JSON-diffable.
2. **After the refactor:** re-render the same fixed dataset through all three systems.
3. **Compare:** pixel-diff (or perceptual diff, given anti-aliasing) the System A/B images and JSON-diff the System C spec, attribute-by-attribute against the tables in §2.1–2.3. Expected outcome: every attribute classified "global token" in §3 should now show identical values across all plot types *within* a system (and, once B is wired to the injected JSON, across systems too); every attribute classified "plot-specific" should show **zero change** from baseline — if a plot-specific value shifts, that's a regression, not an intended consequence of the refactor.
4. **Explicit acceptance list:** because this refactor is expected to *change* several currently-divergent values (e.g. Raincloud's point fill turning black, Box's error-bar unit changing) once Phase 4 is scoped, the diff review should classify each observed change as "expected — this was the divergence being fixed" vs. "unexpected — investigate," using §2's tables as the checklist of what was already known to be wrong.
