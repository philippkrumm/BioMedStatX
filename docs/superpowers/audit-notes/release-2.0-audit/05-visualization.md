## Findings — severity ranked

### MEDIUM

**VZ8 — Raincloud plots always render significance brackets instead of compact-letter display whenever `pairwise_results` is non-empty, unlike Bar/Box/Violin which correctly discriminate by test type.** `src/visualization/datavisualizer.py:1707-1723` (`plot_raincloud`) vs. `339-365` (`_result_uses_brackets`, used by `plot_bar:1013-1020`, `plot_violin:1208-1215`, `plot_box:1415-1422`). `plot_raincloud`'s own inline branch (lines 1710-1717) never calls the shared `_result_uses_brackets` helper. Its `posthoc_method`-string branch (1712) uses an **exact-match** list (`method_lower in ["pairwise t-test", ...]`) instead of the substring/keyword check `_result_uses_brackets` uses, and is missing `wilcoxon`, `paired t-test`, `multivariate-t`, `emm` entirely — but this branch is moot in production because the real call site (`analysis_core.py:1515-1522`) always passes `pairwise_results=pairwise_comparisons`, which triggers the `elif` at line 1715 (`pairwise_results is not None and len(pairwise_results) > 0: show_bars = True`) unconditionally, regardless of whether the underlying post-hoc test is an all-pairs test (Tukey/Games-Howell/Dunn — which should render compact letters per `_result_uses_brackets`'s logic) or a many-to-one test (Dunnett/EMM — which should render brackets). **Impact:** The same statistical result (e.g. a Tukey HSD all-pairs post-hoc) renders as a compact-letter display on a Bar/Box/Violin plot but as brackets on a Raincloud plot of the identical data — a scientist switching plot type in the UI (a single dropdown, no re-analysis) sees the annotation style change without any change in what was actually tested, which is confusing and inconsistent for a publication figure.
**Fix:** Replace `plot_raincloud`'s inline `if posthoc_method... elif pairwise_results...` block (lines 1710-1717) with the same `DataVisualizer._result_uses_brackets(pairwise_results, posthoc_method)` call used by the other three plot types, for parity.

### LOW

**VZ9 — `create_association_tree`, `FlowchartVisualizer.visualize()`, and `FlowchartVisualizer.generate_and_save()` are dead code in production — round 1 characterized these as "the two production call paths," which this round's `git grep` shows is not accurate.** `src/visualization/decisiontreevisualizer.py:131-139` (`create_association_tree`), `src/visualization/flowchartvisualizer.py:140-298` (`visualize`, `generate_and_save`). `create_association_tree` is an **instance** method (`def create_association_tree(self, ...)`), but `DecisionTreeVisualizer` is never instantiated anywhere in `src/` — every real call site uses only `DecisionTreeVisualizer.get_tree_json(...)` as a static/class-level call (`statistical_analyzer_autopilot_ui.py:1022`, `html_exporter.py:326`). `git grep -rn "create_association_tree"` (whole repo) finds exactly one non-definition caller: `validation/test_correlation_transform.py:220,248`, a test file. `FlowchartVisualizer.visualize()` is called only from the now-confirmed-dead `create_association_tree`, and `FlowchartVisualizer.generate_and_save()` has zero callers anywhere, including tests. Its own docstring (flowchartvisualizer.py:28, 291) claims it "matches the `DecisionTreeVisualizer.generate_and_save` API," but `DecisionTreeVisualizer` has no `generate_and_save` method at all (`git grep -n "def " decisiontreevisualizer.py` lists only `_apply_wide_canvas_layout`, `format_dynamic_test_label`, `create_association_tree`, `_mixed_posthoc_node`, `get_tree_json`) — the docstring's claimed sibling method does not exist.
**Impact:** Low — the interactive-canvas path (`get_tree_json`, which round 1 and this round both confirm is correctly gated to 7 named `model_type` values before reaching `FlowchartVisualizer`) is the actual, live rendering path used by both the UI and HTML export. The static-PNG matplotlib rendering path this dead code represents duplicates functionality the HTML/canvas renderer already covers, and is exercised only by one test file. This downgrades round 1's VZ6 (the `_build_topology` silent-typo `else` fallback) even further, since one of its two claimed call paths doesn't fire in production at all.
**Fix:** Either delete `create_association_tree`/`FlowchartVisualizer.visualize`/`generate_and_save` (and update `validation/test_correlation_transform.py` accordingly) if the static-PNG path is confirmed unwanted, or wire it into an actual UI/export call site if it's meant to be a live alternative rendering — and correct the stale `generate_and_save` docstring claim either way.

**VZ10 — 22 additional static utility methods on `DataVisualizer` have zero callers anywhere in `src/`, including two that duplicate live functionality.** `src/visualization/datavisualizer.py:2452-3229` (`set_global_font`, `add_panel_labels`, `annotate_bar_values`, `annotate_box_medians`, `apply_custom_colormap`, `add_reference_line`, `add_inset_axes`, `set_axis_linewidths`, `set_grid_style`, `set_minor_ticks`, `set_tick_format`, `add_stat_bracket`, `add_letter_grouping`, `set_opacity_gradient`, `set_panel_background`, `set_aspect_ratio`, `set_log_axis`, `add_secondary_axis`, `add_broken_axis`, `export_with_metadata`, `add_metadata_block`, `plot_roc_curve`, `plot_forest`). Verified via a per-method `git grep -c` loop excluding self-references: every one returns 0 external callers. Two are true duplicates of live code: `plot_roc_curve`/`plot_forest` (matplotlib, datavisualizer.py:3152-3229) duplicate `src/export/report_charts.py:778` (`_build_roc_chart`, Plotly-based), which is the actual renderer wired into the HTML export pipeline.
**Impact:** Low on its own (no user-facing bug — this is unreachable code, not a wrong-result path), but it inflates the largest file in the codebase (3229 lines) with ~780 lines (24%) of unreferenced surface area, which is a maintenance and review-burden cost: a future contributor could reasonably assume `plot_roc_curve` is the live ROC renderer and modify it, silently fixing nothing.
**Fix:** No urgent action; if a "public visualization API for scripting" use case is intended, document it as such explicitly (e.g. a module docstring note), otherwise remove to shrink the file and reduce confusion. Not a release blocker.

**VZ11 — `apply_custom_colormap`'s greyscale-generation branch divides by zero for `n=1` and `n=0` group counts.** `src/visualization/datavisualizer.py:2480` (`colors = [str(0.2 + 0.6*i/(n-1)) for i in range(n)]`, where `n = len(groups)`) raises `ZeroDivisionError` when `n=1`; `colors[accent_idx % n]` on line 2482 raises `ZeroDivisionError` when `n=0` (before the list comprehension is even reached in that all-`n=0` case the loop body wouldn't execute, but the `accent_idx % n` modulo still evaluates and fails first for `n=0`).
**Impact:** Low — this method has zero callers anywhere in the codebase (see VZ10), so it cannot currently crash a real analysis. Flagged for completeness in case a future single-group scatter/dose-response use case wires this in without noticing the guard is missing.
**Fix:** Guard `n <= 1` (return a single-color list, e.g. `[accent or colormap]`) before the list comprehension, or raise a clear `ValueError("apply_custom_colormap requires at least 2 groups")` — whichever behavior is intended if/when this is wired up.

**VZ12 — The figure watermark feature renders text at a mechanically-verified 1.82:1 contrast ratio against a white background — fails even the lenient 3:1 non-text floor, and fails the 4.5:1 AA text floor for its 8pt (non-large) size by roughly 2.5×.** `src/visualization/datavisualizer.py:2031-2035` (`_add_watermark`): `fig.text(..., fontsize=8, color='gray', alpha=0.5, ...)`. Matplotlib's named color `'gray'` resolves to `#808080`; alpha-blended at 0.5 against white (`#ffffff`) yields an effective rendered color of `#c0c0c0`. WCAG relative-luminance contrast of `#c0c0c0` vs. `#ffffff` = **1.82:1** (computed this session via the standard sRGB relative-luminance formula, `/private/tmp/.../wcag.py`), compared against the un-blended `#808080`'s already-marginal 3.95:1 — round 1 did not check the watermark specifically (it only checked `DEFAULT_COLORS`). The feature is called from all 4 plot types (`plot_bar:1076`, `plot_violin:1265-1266`, `plot_box:1472-1473`, `plot_raincloud:1765-1767`) whenever `watermark` is truthy, but `watermark` is never populated by `plot_from_config`'s `base_kwargs` (datavisualizer.py:2833-2885) or by any UI dialog found in this batch — so it is currently dormant (`None` on every live code path checked), not a live user-facing failure today.
**Impact:** Low today (dormant feature), but a latent trap: if a watermark/branding feature is wired to the UI later (a plausible next feature for a "publication-ready export" product), the text would be nearly invisible on export, especially at small preview sizes or when printed.
**Fix:** Either drop the `alpha=0.5` (matplotlib alpha blends toward the axes/figure background, not a fixed overlay — dropping it and using a darker gray like `#595959` at full opacity would restore ≥4.5:1) or pick a WCAG-compliant muted color combination before wiring this feature to any UI control.

- **The coordinate-based `_grouped_bar_centers` (datavisualizer.py:470-494) is well-designed defensive code**: it maps each rendered bar to its (between, within) cell by actual pixel/data coordinates rather than by patch index, specifically so that a missing/all-NaN cell (which seaborn simply omits) cannot silently shift and mis-place other cells' significance brackets.
