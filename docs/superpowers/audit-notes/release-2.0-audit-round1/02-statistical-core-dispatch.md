# AUDIT: BioMedStatX — Statistical Core Dispatch @ b16cf24

**Scope:** `src/analysis/analysis_core.py` (1592 lines), `src/analysis/statisticaltester.py`
(2915 lines), `src/analysis/clinical_models.py` (2040 lines). Cross-references into
`src/statistical_testing/mixed_assumptions.py`, `src/statistical_testing/advanced_pipeline.py`,
and `src/export/report_stat_rows.py` were followed only as far as needed to confirm whether a
correction computed in the three assigned files is actually wired to the value a user sees;
those files' own internals are out of this batch's scope.

**Verdict.** The core dispatch is fundamentally sound — DF/p-value pairing inside a single
ANOVA table row is consistently correct, effect-size formulas spot-checked against textbook
definitions are right, and the CHANGELOG's "conservative default" and "ddof=1" guarantees hold
for every case *except* one: Mixed ANOVA's sphericity correction is computed but not wired into
the canonical `p_value` used for the significance decision and post-hoc trigger, an unfixed
sibling of the RM-ANOVA bug this session already patched. Logistic Regression also never got
the same "omnibus test as main p-value" fix that Beta Regression received — it still reports
the first predictor's p-value as the headline result. No CRITICAL findings; two HIGH findings
that silently affect which results are called "significant" and trigger post-hoc testing.

## Findings — severity ranked

### HIGH

**SC1 — Mixed ANOVA's sphericity correction is computed and shown in the effects table, but the top-level `p_value` used for the significance verdict and post-hoc trigger stays uncorrected.**
`src/analysis/statisticaltester.py:1548-1555` sets `results["p_value"]` from the interaction row's **uncorrected** `p_col` (pingouin's `p_unc`/`p-unc`) inside `_run_mixed_anova`. `results.update(within_sphericity_results)` at line 1569 merges in `within_sphericity_corrections` / `within_correction_used` / nested `main_effect.final_p_value` from `MixedAnovaAssumptionEngine._test_mixed_anova_within_sphericity` (`src/statistical_testing/mixed_assumptions.py:387-499`) and `_apply_mixed_anova_sphericity_corrections` (line 570), but nothing in `_run_mixed_anova`, `_run_any_parametric_test`, or `advanced_pipeline.py` ever does the RM-ANOVA-style rewrite `results["p_value"] = <corrected>` that exists at `statisticaltester.py:1973-1974` for the RM-ANOVA path. Confirmed with `grep -n "within_corrected_p_value\|final_p_value"` across `statisticaltester.py`, `mixed_assumptions.py`, `advanced_pipeline.py` — no assignment back to `results["p_value"]` or `results["interactions"][0]["p_value"]` exists anywhere.

**Downstream consequence:** `src/export/report_stat_rows.py:428-437` (and the parallel interaction-row block at 472-485) DOES read `within_sphericity_corrections` and substitutes the corrected df/p into that one effects-table row, with a "(GG)"/"(HF)" suffix — so a careful reader who checks the detailed ANOVA effects table sees the right, corrected number. But `analysis_core.py:1087` (`test_results['p_value'] < 0.05` — gates post-hoc), the "Significant (p < 0.05)" text in the analysis log (`analysis_core.py:1351`), `StatisticalTester.nonfinite_block`, and the cross-dataset FDR correction (`analysis_core.py:361-392`) all read the *uncorrected* top-level `p_value`. Net effect: a Mixed ANOVA whose interaction/within-factor effect is significant only under the uncorrected p (but not after GG/HF correction, or vice versa) will silently trigger post-hoc tests, "Significant" wording, and FDR-family membership on the wrong basis, while the effects table two sections later shows a contradicting corrected p-value in the same report. This is exactly the same bug class as the already-fixed RM-ANOVA sphericity bug and the already-fixed ANCOVA control_group bug: a correct computation that never reaches the decision path that matters.
**Fix:** In `_run_mixed_anova` (statisticaltester.py, right after `results.update(within_sphericity_results)` at line 1569), mirror the RM-ANOVA pattern: if `within_sphericity_results` indicates a correction was applied to the interaction (or to the within main-effect, when the interaction isn't the reported effect), overwrite `results["p_value"]` and `results["interactions"][0]["p_value"]` / `results["factors"][...]["p_value"]` with the corrected value before it is returned, exactly as `sphericity_results.get("final_p_value")` is already special-cased for RM-ANOVA.

**SC2 — Logistic Regression still reports the first predictor's p-value as the headline result; the omnibus-LR fix the CHANGELOG documents for Beta Regression was never applied to Logistic Regression.**
`src/analysis/clinical_models.py:1526-1530`: `LogisticRegressionModel.as_results_dict()` sets `main_p = or_table[0]["p_value"]` unconditionally — the p-value of whichever coefficient `odds_ratios()` happens to list first. Compare `BetaRegressionModel.as_results_dict()` (clinical_models.py:1697-1727), which the CHANGELOG explicitly calls out as fixed: it prefers `self.result.llr_pvalue` (an omnibus likelihood-ratio test against the null model) and only falls back to "first predictor" when the LR p-value is unavailable. Verified statsmodels' `GLMResults` (the class backing `LogisticRegressionModel.result`) does **not** expose `llr`/`llr_pvalue` the way `BetaModel`'s results class does, but it does expose `llf` and `llnull` (statsmodels confirmed via introspection: `dir(GLMResults)` → `['llnull', 'null', 'null_deviance']`), and both are already read in the same method (line 1535-1536) to compute McFadden's pseudo-R². The omnibus LR statistic `2*(llf - llnull) ~ chi2(df_model)` is a two-line computation from data already in scope; it is simply never built.
**Impact:** for any logistic regression with ≥2 predictors/covariates, the reported "main" p-value depends on coefficient ordering (whichever the model's design matrix lists first — typically alphabetical/insertion order from the formula, not a methodologically meaningful "primary" predictor), not on whether the model as a whole is significant. This is a materially misleading headline statistic for the same reason the CHANGELOG says the Beta Regression version was.
**Fix:** In `LogisticRegressionModel.as_results_dict()`, compute `llr_stat = 2*(self.result.llf - self.result.llnull)`, `df_model = self.result.df_model` (or `len(predictors)+len(covariates)`), `llr_p = chi2.sf(llr_stat, df_model)`, and use that as `main_p`/`p_value_note="Omnibus (Likelihood-Ratio)"` when the standard (non-Firth) model converged, falling back to first-predictor only when `llnull` is unavailable (mirrors the Beta Regression branch exactly). For the Firth-fallback branch, no `llnull` exists — document the fallback explicitly rather than silently reusing first-predictor without a note (currently there is no `p_value_note` field on Logistic Regression at all, unlike Beta Regression).

### MEDIUM

**SC3 — Mixed ANOVA's between-factor variance-homogeneity tests (Levene/Brown-Forsythe/Bartlett/Welch) are computed but purely informational; the main test never switches off the standard pingouin `mixed_anova` call even when variances are clearly unequal.**
`src/statistical_testing/mixed_assumptions.py:32-123` (`_test_mixed_anova_between_assumptions`) runs 4 variance tests and a Welch-ANOVA-on-the-between-factor computation, but the result only populates `results["between_assumptions"]` (nested, informational) — `_run_mixed_anova` (statisticaltester.py:1470+) always uses `pg.mixed_anova(...)`, which assumes homogeneity of the between-factor's variance, regardless of what these checks find. This is different in kind from SC1 (nothing is silently mis-displayed — the recommendations are visible to the user in the nested dict), but it means "Welch's ANOVA (unequal variances correction)" is computed and then discarded rather than acted on, unlike the equivalent one-way/two-way code paths in this codebase that do switch tests. Low urgency since Mixed ANOVA with heterogeneous between-group variance is a narrower edge case, but worth tracking since it's inconsistent with the rest of the codebase's assumption-driven dispatch philosophy.
**Fix (if in scope for 2.0):** either wire a robust alternative when between-factor Levene/Brown-Forsythe indicates violation (mirrors the Games-Howell / Welch-ANOVA dispatch already used for one-way designs), or explicitly document in the exported report that Mixed ANOVA's between-factor variance-homogeneity check is diagnostic-only in this release.

### LOW

**SC4 — LMM's "Between-Within" degrees-of-freedom correction is labeled "Kenward-Roger / Satterthwaite approximation" but implements neither.**
`src/analysis/clinical_models.py:769-770`: `df_method = "Between-Within (Kenward-Roger / Satterthwaite approximation)" if apply_correction else "Asymptotic (z-test)"`. The actual computation at lines 779-793 is a simple between-within heuristic (`n_groups - 1 - n_between_predictors` for between-subject terms, `n_obs - n_groups - n_within_predictors` for within-subject terms) applied only to the *degrees of freedom* used to convert the existing asymptotic z-statistic into a t-statistic — it does not adjust the standard error the way true Kenward-Roger does, and it isn't the Satterthwaite formula (which would need per-parameter variance components, not a single group-count-based df). The label overstates the rigor of what's actually a reasonable but much simpler approximation. Internally consistent (the same `df_param` feeds both the p-value and the CI, so no p-value/CI mismatch), just potentially misleading to a reader who takes the label at face value when deciding how much to trust small-sample inference.
**Fix:** Rename the label to something accurate, e.g. `"Between-Within degrees-of-freedom approximation"`, and drop "Kenward-Roger / Satterthwaite" unless those specific corrections are implemented (they would also need statsmodels' more advanced covariance-adjustment machinery, not just a df substitution).

**SC5 — `clinical_models.py:542` `.get("F", 0)` default would silently substitute F=0 rather than error if a statsmodels ANOVA table ever omitted the "F" column.**
`float(row.get("F", 0)) if pd.notna(row.get("F")) else None` in `ANCOVAModel.as_results_dict` (the `anova_rows` loop). Currently unreachable — `anova_lm(model, typ=3)` always includes an "F" column for the between-factor rows this loop iterates. Flagged only because it's the exact shape of "library version bump silently changes return shape, code swallows it" the audit was asked to check for; no live impact today.
**Fix:** replace the bare `.get("F", 0)` default with an explicit `KeyError`/log-and-skip if the column is genuinely absent, so a future statsmodels change surfaces rather than reports a false F=0.

## Strengths (verified)

- **RM-ANOVA sphericity correction is fully and correctly wired** (statisticaltester.py:1966-1993, 2582-2896): Mauchly's test → GG/HF correction → `final_p_value` → `results["p_value"]` rewrite, with an outer-exception fallback that still applies the documented conservative GG default (statisticaltester.py:2690-2711) rather than silently reverting to the uncorrected p — this is the fix from earlier this session, confirmed still in place and confirmed to be the *only* one of the two sphericity paths (RM vs. Mixed) that got it.
- **Hedges' g / J-correction formula is correct and consistent** across the two independent implementations (statisticaltester.py:594, posthoc_core.py:1462) — algebraically identical `1 - 3/(4·df - 1)` form, matching Hedges & Olkin (1985), applied uniformly to both the Welch's-t-test-Hedges'-g path and the Games-Howell path.
- **ANCOVA and LMM both correctly thread `control_group` end-to-end** from the UI callback (`analysis_core.py:600-611, 622-636`) through `model.fit()` into `emm_contrasts(method="vs_control")` — the exact wiring gap this session already found and fixed for ANCOVA has not regressed, and LMM (built on the same pattern) never had the gap in the first place.
- **`nonfinite_block` safety net** (statisticaltester.py:64-94) is a clean, well-placed universal chokepoint: it runs after every advanced-engine dispatch (LMM/RM/Mixed/Two-Way ANOVA/ANCOVA) in `analysis_core.py:1297-1301` and blocks non-finite statistics/out-of-range p-values before they can reach the report, closing off a class of "degenerate design silently reports a garbage p-value" bugs across all the clinical models in one place rather than requiring each model to self-police.
- **DF and p-value are always extracted from the same table row** in every ANOVA-table-based test path checked (Welch ANOVA, Two-Way ANOVA, ANCOVA, RM-ANOVA main effect) — no instance found of a p-value and its accompanying df coming from mismatched sources.
- **Firth penalized-likelihood fallback for logistic regression separation** (clinical_models.py:1121-1265) is genuinely well-built: penalized likelihood-ratio p-values and penalized profile-likelihood CIs (both documented as matching R's `logistf` default inference) are preferred over the unreliable Wald statistics that would otherwise be reported under separation, with an explicit `ci_method`/`p_value_method` field so the report discloses which was used.

## Recommended remediation order

1. **SC1 (Mixed ANOVA sphericity wiring)** — highest value, smallest diff: the RM-ANOVA fix from this session is a near-exact template (`sphericity_results.get("final_p_value")` → `results["p_value"]` rewrite). Fixing this also resolves the report-internal contradiction between the effects table and the top-level verdict.
2. **SC2 (Logistic Regression omnibus p-value)** — same shape as the Beta Regression fix already shipped this session; `llf`/`llnull` are already in scope in the method, so this is a small, self-contained addition with a direct CHANGELOG precedent to follow.
3. **SC4 (LMM df-method label)** — one-line doc/string fix, zero risk, do opportunistically alongside SC1/SC2 since it's in the same file.
4. **SC5 (`.get("F", 0)` hardening)** — low priority, bundle with any other defensive-parsing cleanup pass rather than a standalone PR.
5. **SC3 (Mixed ANOVA between-factor Welch dispatch)** — needs a design decision (auto-switch vs. document-as-diagnostic-only), not a pure bugfix; defer to a product discussion rather than rushing before 2.0 if time is short, but track it since it's a real methodological gap once flagged.
