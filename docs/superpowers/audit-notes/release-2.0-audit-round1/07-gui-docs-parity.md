## Findings — severity ranked

### HIGH

**GD1 — The `mixed_anova` Help Hub recipe asserts a "conservative correction" guarantee that does not hold for Mixed ANOVA.**
`src/core/help_content.py:282`: *"If that equal-footing assumption for the time factor cannot be confirmed, the app applies a conservative correction rather than assuming it holds."* This is word-for-word the same claim made (correctly) for RM-ANOVA at `help_content.py:219`. But the parallel `02-statistical-core-dispatch.md` audit run this session (finding **SC1**) mechanically confirmed that Mixed ANOVA's sphericity correction is computed (`mixed_assumptions.py:387-499`, `_apply_mixed_anova_sphericity_corrections`) and surfaces correctly in the *effects table* (`report_stat_rows.py:428-437`), but is **never written back** to the top-level `results["p_value"]` that gates the "Significant" verdict, the post-hoc trigger (`analysis_core.py:1087`), and FDR-family membership — unlike RM-ANOVA, which does get this rewrite (`statisticaltester.py:1966-1993`). A user reading this recipe is told the app defaults to a conservative correction for Mixed ANOVA specifically; in the one case that matters (sphericity violated or untestable), the significance decision they see is silently based on the **uncorrected** p-value instead.
**Impact:** a user relying on the Help Hub's stated behavior to trust the Mixed ANOVA significance verdict is misled in exactly the edge case the recipe calls out as handled.
**Fix:** either (a) fix the underlying code per SC1's recommendation in `02-statistical-core-dispatch.md` (mirror the RM-ANOVA `results["p_value"]` rewrite in `_run_mixed_anova`), which would make the recipe true again, or (b), if the code fix is deferred past 2.0, soften `help_content.py:282` to note the correction is currently informational-only for Mixed ANOVA (effects table) rather than decision-driving. Prefer (a) — it's a small, well-scoped fix with a direct template already in the codebase, and leaves both the code and the docs consistent without special-casing the recipe text.

### MEDIUM

**GD2 — `ColumnSelectionDialog`'s "multi-dataset" checkbox is dead code that contradicts CLAUDE.md's own "already removed" claim.**
`src/ui/dialogs/statistical_analyzer_dialogs.py:390-449`: the class (and its `self.multi_dataset_check = QCheckBox("Separate analysis per dataset with shared HTML report")` at line 409) is fully built but never imported or instantiated anywhere in `src/` or `tests/` (`grep -rn "ColumnSelectionDialog" src/ tests/` returns only the class's own definition and its internal error string). `CLAUDE.md:87` states: *"The classic plot workflow, multi-dataset button, and old `init_ui` body have already been removed. Don't reintroduce them."* — this class is exactly the kind of surviving dead surface that claim says shouldn't exist. Not reachable today so no user-facing risk, but it is maintenance debt masquerading as live code (a future contributor grepping for "multi-dataset" to understand current behavior will find this and be misled about what's actually wired up), and it directly falsifies the CLAUDE.md sentence next to it.
**Fix:** delete `ColumnSelectionDialog` (and its now-orphaned `get_selected_columns`/`multi_dataset_check` machinery) in the same PR that next touches this file, or — if some external/CLI caller still needs it — document that caller in CLAUDE.md instead of the current unconditional "removed" claim.

**GD3 — `InteractiveDecisionTreeWidget` has no keyboard-accessible zoom or reset-view control.**
`src/ui/components/decision_tree_view.py:404-415`: zoom is wired exclusively through `wheelEvent` (mouse wheel); `QGraphicsView`'s default keyboard scrolling (arrow keys) still works, but there is no keyboard equivalent for zoom-in/zoom-out/fit-to-view, and `src/autopilot/statistical_analyzer_autopilot_ui.py:969` labels the panel "Pan and zoom" with no mention of a keyboard path — because none exists (`grep -rn "InteractiveDecisionTreeWidget\|refit_view" src/` shows the only zoom entry points are the wheel event and the programmatic `refit_view()` called after analysis, never bound to a keypress or button). This is the decision-tree visualization only (supplementary, not a required workflow control), so MEDIUM rather than HIGH.
**Fix:** bind `+`/`-`/`0` (or similar) to zoom-in/zoom-out/refit when the widget has focus, mirroring the existing `wheelEvent` factor logic and `refit_view()`.

**GD4 — `ExploratoryMatrixDialog`'s multi-select variable list has an undiscoverable keyboard interaction.**
`src/ui/dialogs/statistical_analyzer_dialogs.py:931-939`: `QListWidget.MultiSelection` mode means arrow keys move the current-item highlight without toggling selection — a keyboard-only user must know to press Space at each item to (de)select it, and nothing in the UI (no label, no tooltip) states this. Low severity since the list is pre-selected-all by default and the dialog is still fully keyboard-operable once the interaction model is known.
**Fix:** add a one-line hint under the label ("Space toggles a row; all variables are selected by default") or switch to `QListWidget.ExtendedSelection` with visible checkboxes, which telegraphs the interaction model more clearly.

### LOW

**GD5 — CLAUDE.md's `_ap_*` pipeline line-number citations have drifted.**
CLAUDE.md cites `_ap_browse_file (pipeline:822)`, `_ap_load_file (pipeline:832)`, `_ap_load_sheet (pipeline:875)`; actual current lines are 930, 940, 1025 (`grep -n "^def _ap_browse_file\|^def _ap_load_file\|^def _ap_load_sheet" src/autopilot/statistical_analyzer_autopilot_pipeline.py`). CLAUDE.md was last edited 2026-05-26; the pipeline file has grown to 2341 lines / 43 `_ap_*` functions since. The architectural claims (which methods live where, mixin binding) are still accurate — only the specific line numbers are stale. Low impact (a reader following the reference lands ~100 lines off, in the same function-dense region) but a repeat of the same staleness pattern the project has already been bitten by once.
**Fix:** either drop the specific line numbers from CLAUDE.md (name the function, not the line — line numbers in prose docs rot by construction) or add a lightweight recurring check (e.g. a one-line `grep -n` re-verification) before each release.

**GD6 — `ComparisonSelectionDialog.get_selected_comparisons()` allows an empty confirm with no warning.**
`src/ui/dialogs/comparison_selection_dialog.py:81-86`: clicking OK with every checkbox unchecked returns `[]` silently — no `QMessageBox.warning` the way `GroupSelectionDialog.get_selected_groups()` (`statistical_analyzer_dialogs.py:120-124`) and `ColumnSelectionDialog.get_selected_columns()` (`:441-444`) both have for the equivalent "nothing selected" case. Low risk (the caller in `analysis_core.py` presumably no-ops on an empty list rather than crashing), but it's an inconsistency with the pattern used everywhere else in this file family.
**Fix:** add the same `if not selected: QMessageBox.warning(...)` guard used by the sibling dialogs, for UI consistency.

**GD7 — `_apply_log_scale_gating`'s tooltip updates regardless of whether "Log Y" is even checked.**
`src/ui/dialogs/plot_aesthetics_dialog.py:1580-1600`: the has-nonpositive-values scan and tooltip assignment run unconditionally at dialog construction, independent of `self.style_tab.logy_check.isChecked()`. Not a bug — the tooltip is accurate framing regardless of current checkbox state ("will be used automatically" — i.e., if/when the user turns it on) — but worth a one-line comment noting this is intentional (advisory tooltip, not a live status), since a future maintainer might assume it should gate on the checked state.
