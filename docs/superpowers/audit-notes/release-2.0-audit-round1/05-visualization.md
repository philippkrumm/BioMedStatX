# AUDIT: BioMedStatX — Visualization / Plotting Engine @ b16cf24

**Verdict.** No live emergency. The plotting engine is functionally solid and two real
Fault-Swallowing bugs from earlier in this session (grouped-EMM silent bar fallback, log-axis
silent data loss) are genuinely fixed with visible on-canvas annotations. However, the same
anti-pattern recurs in at least one more clearly reachable spot: `_add_significance_letters`
wraps its entire compute-and-draw block in a bare `except Exception` that only logs — a `KeyError`
or similar failure there silently produces a publication plot with **zero significance
annotations** and no visual cue that anything is missing. There is also a real, mechanically
verified WCAG contrast failure in the default categorical palette, an un-fixed asymmetry between
the `logx` and `logy` non-positive-data handling, and several NaN-unsafe p-value format strings
that render the literal string `"nan"` on a plot/report instead of erroring or flagging it.

## Findings — severity ranked

### HIGH

**VZ1 — `_add_significance_letters` / `_add_significance_letters_raincloud` swallow ALL letters on any exception, with zero on-canvas indication.** `src/visualization/datavisualizer.py:2314-2386` (flat plot) and `2389-2449` (raincloud). The entire letter-computation-and-draw block — including `get_significance_letters_from_posthoc`, mean/error computation, and the final `letters[group]` lookup at line 2372/2437 — is wrapped in one `except Exception: logger.error(...); traceback.print_exc()`. A `KeyError` on `letters[group]` (reachable if `get_significance_letters_from_posthoc` doesn't populate a key for every element of `groups` — e.g. a group present in the plot but absent from every `pairwise_results` comparison and not the Dunnett control) silently drops **every** significance letter from the figure. The bar/box/violin/raincloud plot itself renders successfully and looks complete; only a backend log line (`logger.error`, not shown in the UI) records the failure. This is the exact "plot silently renders something different/wrong instead of erroring or visibly flagging it" pattern already fixed twice elsewhere this session (grouped-EMM fallback, log-axis data loss).
**Impact:** A publication figure can ship with no significance letters at all, and nothing about the rendered PNG/SVG signals that annotation failed — a scientist could report "no significant differences shown" when the letters were simply never drawn.
**Fix:** Catch narrower exceptions where feasible; on any failure, call `DataVisualizer._draw_warning_annotation(ax, "Significance letters could not be computed: <reason>")` (the mechanism already exists and is used for the log-axis and grouped-EMM fixes) instead of only logging.

### MEDIUM

**VZ2 — Two independent silent-drop paths can under-count significance brackets relative to `pairwise_results` without any on-canvas indication.** (a) `_grouped_bracket_positions` (datavisualizer.py:497-533): for each `comp`, if either group doesn't resolve via `label_map`/`centers` (e.g. an all-NaN interaction cell seaborn didn't render a patch for), the comparison is `continue`d — silently dropped (docstring at line 503-504 says "skipped (defensive)", i.e. this is a known, accepted behavior, but it's invisible to the end user). (b) `_calculate_bracket_positions` (datavisualizer.py:646-733): if either `g1`/`g2` from a comparison isn't in `group_pos` (reachable when `plot_bar`/`plot_box`/`plot_violin` filter `groups` to drop any group with zero valid samples — lines 907-910, 1139-1142, 1332-1335 — while `pairwise_results` computed upstream by the stats engine still references the dropped group), that comparison is silently excluded from the `comparisons` list at line 668 and never gets a bracket.
**Impact:** In both cases the number of brackets drawn can legitimately be less than `len(pairwise_results)`, and the figure looks complete (well-formed, correctly-spaced brackets) rather than visibly incomplete — this is precisely the "desync without anyone noticing" failure mode named in the audit brief.
**Fix:** Track and report the count of dropped comparisons (e.g. accumulate a list of `(comp, reason)` in both functions) and call `_draw_notice_annotation`/`_draw_warning_annotation` when `len(dropped) > 0`, naming how many comparisons were omitted and why.

**VZ3 — `logx` non-positive-data handling was not brought up to the same standard as the `logy` fix; it still only warns-and-drops instead of auto-adapting to symlog.** `src/visualization/datavisualizer.py:1898-1904` vs. `1906-1927`. The `logy` branch (fixed this session) auto-computes a `linthresh` via `_analyze_nonpositive_values` and switches to `symlog` when possible, falling back to plain-log-plus-warning only in the genuine all-zero degenerate case. The `logx` branch three lines above does neither of those two things — it unconditionally sets `ax.set_xscale('log', base=10)` and, if any non-positive x-values exist, only calls `_draw_warning_annotation` (never `_draw_notice_annotation`/symlog). This is an intentional-looking asymmetry left over from the fix (the session's commit history shows the symlog work landed specifically for the y-axis: `01a1e626` "auto-apply symlog scale for log-axis data" and `5007b9d` "add data-driven linthresh helper" both reference y-axis usage sites only).
**Impact:** Any plot with `logx=True` and non-positive x-values (used for e.g. Raincloud plots and the log-x parameter path) still silently drops those points on a plain log scale rather than getting the lossless symlog treatment the y-axis now has — data loss the user has to notice from the (correctly-shown) warning text rather than the plot preserving the points.
**Fix:** Mirror the `logy` branch's logic for `logx`, reusing `_analyze_nonpositive_values`/`SymmetricalLogLocator`/`LogFormatterMathtext` against the x-axis.

**VZ4 — `DataVisualizer.DEFAULT_COLORS` fails WCAG non-text contrast (3:1) against a white background for 2 of 6 colors, and is reachable as the actual rendered palette.** `src/visualization/datavisualizer.py:798`: `['#3357FF', '#FF5733', '#33FF57', '#F033FF', '#FF3366', '#33FFEC']`. Mechanically verified: `#33FF57` (bright green) = 1.35:1, `#33FFEC` (cyan) = 1.26:1 against `#FFFFFF` — both fail even the lenient 3:1 non-text floor (WCAG 1.4.11) by more than 2×; three more (`#FF5733`, `#F033FF`, `#FF3366`) clear 3:1 but fail the 4.5:1 text-equivalent bar relevant when these colors carry legend text/labels. This palette is the fallback in all four plotting entry points (`plot_bar` 901/924, `plot_violin` 1130, `plot_box` 1323, `plot_raincloud` 1549) whenever `colors=None` and no `color_palette` override captures the call — i.e. any direct/programmatic call to these methods without explicit colors, not just the UI path (the UI path has its own, WCAG-clean fallback palette in `plot_preview.py:203`, verified separately: all ≥3.64:1). Also relevant for colorblind-safety: green (`#33FF57`) and a saturated red-orange (`#FF5733`)/pink-red (`#FF3366`) sitting in the same 6-color set risk confusability for red-green color-vision deficiency in a scientific figure meant for print/publication.
**Impact:** A bar/box/violin/raincloud rendered via direct API call (bypassing the UI's own color config) with the library default palette can produce a fill so pale it is nearly invisible against a white page/print background, and is more likely to be ambiguous for colorblind readers.
**Fix:** Replace `#33FF57`/`#33FFEC` with the same journal-safe hues already defined in `StylingManager._apply_seaborn_base`'s `journal_palettes` dict (e.g. `Nature`/`Science` sets, already contrast-checked at 3.15–6+:1 based on the earlier `apply_custom_colormap` accent `#0072B2`), or reuse the `plot_preview.py:203` palette as `DataVisualizer.DEFAULT_COLORS`.

### LOW

**VZ5 — NaN p-values silently render as the literal string `"p = nan"` and are treated as "not significant" across all three visualization files, rather than being flagged.** Confirmed sites: `datavisualizer.py:405-435` (`_format_p_value_label`, used for brackets — `p_value < 0.001` etc. all evaluate `False` for NaN, falling through to `'n.s.'`, itself misleading), `datavisualizer.py:3211/3215` (forest plot: `p_val < 0.05` → `False` → renders gray/"not significant" color; `f"p = {p_val:.4f}"` → literal `"p = nan"`), `decisiontreevisualizer.py:69` (`p_val < 0.0001` → `False` → `f"p = {p_val:.4f}"` → `"p = nan"`), `flowchartvisualizer.py:56` (`_fmt_p`, same pattern), and every `p_value < alpha` significance branch in both tree-topology builders (e.g. flowchartvisualizer.py:330, decisiontreevisualizer.py:492/496/500/511 etc.) — a NaN `p_value` silently takes the "not significant" branch of the decision tree/flowchart, which could misrepresent the actual analysis path taken.
**Impact:** Does not crash (verified: `f"{float('nan'):.4f}"` returns `'nan'`, no exception), but produces a garbage-looking label on a scientific figure/report and can silently mis-render which branch of a decision tree was "taken" if a p-value is ever NaN (e.g. from a degenerate/failed sub-test upstream).
**Fix:** Add an explicit `p_value != p_value` (or `math.isnan`) guard before each comparison/format site; render `"p = N/A"` or a distinct warning glyph instead of a numeric-looking NaN string, and route the significance branch to an explicit "undetermined" state rather than defaulting to "not significant."

**VZ6 — `FlowchartVisualizer._build_topology`'s `else` branch silently renders a CorrelationMatrix-shaped topology for any unrecognized `model_type`, with no visible "unknown type" indication.** `src/visualization/flowchartvisualizer.py:638-669`. Comment says "CorrelationMatrix (and any unrecognised type)" — this is a deliberate catch-all, not an oversight, but it means a typo'd or newly-introduced `model_type` string produces a *structurally different, silently substituted* diagram rather than an error or a visible "type not recognized" node. In practice this path is only reached via `FlowchartVisualizer.visualize()`/`generate_and_save()` called directly (`decisiontreevisualizer.py:138-139`, `164-167`), not through the documented 7-type contract that `get_tree_json()` enforces at the caller (`decisiontreevisualizer.py:164-165`), so the blast radius is small.
**Impact:** Low — mostly a documentation/intent gap rather than a live bug, since the two production call paths (`get_tree_json` for the interactive canvas, `create_association_tree` for the static PNG) both only ever pass one of the 7 known types today.
**Fix:** Either rename the branch/comment to make the fallback-vs-CorrelationMatrix distinction explicit, or raise/log a warning distinguishable from an actual CorrelationMatrix request when `model_type not in (known types)`.

**VZ7 — Cosmetic-only `except Exception: pass`/log-only sites are numerous but low-risk (documented for completeness).** `_get_plot_max_height_robust` (datavisualizer.py:298,311,321,329 — swallow to `pass`, each is one of 5 redundant height-detection strategies with a final `1.0` fallback, so failure here degrades bracket/letter Y-positioning at worst, never data correctness), `_get_group_extents` (line 465 — falls back to an evenly-spaced-groups assumption, cosmetic bracket-x-position degradation only), `_apply_axis_offset`/`_format_axes` offset-axes and axis-break-marker try/excepts (lines 240, 1695, 1963-1968, 1970-1976 — a cosmetic spine-offset or a break marker simply doesn't render; the underlying data and axis scale are unaffected), `_apply_padding_mm` (3111 — cosmetic margin), `_apply_grayscale_preview`'s `_to_gray` (3124 — falls back to original, non-grayed color, which is arguably the *safer* failure direction for a "designer contrast check" feature), `_lazy_get_output_path` (line 19 — falls back to CWD-relative save path, functionally fine), `FontManager.apply_font_safely` (110-116 — falls back to Arial, a real font, visually distinguishable only by typeface not content). None of these misrepresent statistical results; they degrade only presentation polish. Ranked LOW/no-action rather than omitted, per the "every finding is falsifiable" rule — flagged so the reader can distinguish "checked and fine" from "not checked."
**Impact:** Negligible — no data or significance-result misrepresentation.
**Fix:** No action needed; optionally add a debug-level log noting which of the 5 height-detection strategies actually fired, for future maintainability.

## Strengths (verified)

- **The two Fault-Swallowing bugs fixed earlier this session are genuinely fixed and hold up on re-read.** `_grouped_emm` (datavisualizer.py:2930-2952): on failure, falls back to `plot_bar` **and** calls `_draw_warning_annotation` with an explicit "Structural Warning" message — verified this survives to the rendered figure (`_draw_warning_annotation`, datavisualizer.py:2584-2597, draws directly on `ax` with `zorder=1000, clip_on=False`, so it exports with the PNG/SVG rather than only appearing in a log). The `logy` non-positive-value handling (datavisualizer.py:1906-1927) correctly distinguishes the lossless symlog-auto-adapt case (`_draw_notice_annotation`, neutral gray styling) from the genuine-data-loss case (`_draw_warning_annotation`, red styling) — a well-designed two-tier signal, not a blanket warning.
- **`plot_from_config`'s plot-type dispatch is exception-consistent with its sibling.** Unlike the flowchart's soft catch-all, the actual plot-type dispatcher (datavisualizer.py:2904-3009) raises `ValueError(f"Unbekannter plot_type: {plot_type}")` for anything outside Bar/Box/Violin/Raincloud — matches the equivalent `error_style` dispatch a few lines earlier (line 944-949) which also raises `ValueError` for an unrecognized value. No silent-default disagreement found in this batch.
- **`plot_preview.py`'s top-level exception handler does the right thing.** `update_plot`'s `except Exception as e` (plot_preview.py:230-237) draws the actual error message in red directly on the preview canvas (`f'Error while drawing:\n{str(e)}'`) rather than silently leaving a stale or blank preview — this is the correct pattern the other fault-swallowing findings above should be brought up to.
- **`get_tree_json() -> None` is correctly handled by its primary UI caller.** `statistical_analyzer_autopilot_ui.py:1021-1029` treats a `None` return as an explicit failure (`raise ValueError`, caught immediately, surfaced via `show_placeholder(f"Decision tree could not be rendered: {exc}")`) rather than rendering an empty/misleading tree widget.
- **`selected_pairs` filtering is centralized and applied once, upstream of both letters and brackets** (datavisualizer.py:2887-2898), so there is no risk of the two annotation styles (compact-letter display vs. brackets) disagreeing about which comparisons survived a user's manual pair selection — both consume the identically-filtered `pairwise_results` list.
- **The `_analyze_nonpositive_values` docstring (datavisualizer.py:2529-2546) is a model of the kind of reasoning documentation this codebase should have more of** — it explains *why* the 5th percentile (not min) is used for `linthresh`, anticipating a single pipetting-error artifact collapsing the threshold. Good scientific-software hygiene.

## Recommended remediation order

1. **VZ1** (HIGH) — bring `_add_significance_letters`/`_add_significance_letters_raincloud` up to the same visible-failure standard as the already-fixed grouped-EMM and log-axis paths; this is the same bug class, same file, same session's stated hunting target, and cheapest to fix (one `_draw_warning_annotation` call added to an existing except block, mirroring code already in the file).
2. **VZ3** (MEDIUM) — extend the just-shipped `logy` symlog fix to `logx` for API/behavioral parity; the helper functions (`_analyze_nonpositive_values`, `_draw_notice_annotation`) already exist and just need a mirrored call site.
3. **VZ4** (MEDIUM) — swap the two failing hex colors in `DataVisualizer.DEFAULT_COLORS`; a one-line constant change, no logic risk.
4. **VZ2** (MEDIUM) — add dropped-comparison counting + a notice annotation to both bracket-position builders; slightly more involved since it touches two functions, but same annotation mechanism as #1.
5. **VZ5** (LOW) — add NaN guards at the ~8 p-value format/compare sites; mechanical, low-risk, but touches three files so budget a bit more review time.
6. **VZ6** (LOW) — comment/logging clarification only; no functional change required unless a new `model_type` value is anticipated soon.
7. **VZ7** (LOW/no-action) — no fix needed; keep as documented-and-verified for the release notes.
